# AutoShiftMaker 詳細設計書

## 1. フロントエンド詳細設計（app.js）
### 1.1 初期化
- DOM要素を取得し、現在年月を対象月に初期設定。
- `loadPatterns()` でローカルストレージから勤務体系を復元。
- `renderPatterns()`, `renderWorkers()` を実行して初期描画。

### 1.2 勤務体系管理
- `addPattern` クリック時:
  - 入力検証（名称、時刻範囲）と翌日公休チェック状態を取得。
  - 一意ID付き勤務体系オブジェクトを生成し配列へ追加。
  - `savePatterns()` で保存後、再描画。
- 削除ボタン押下時:
  - 対象勤務体系を配列から除外。
  - 全勤務者の `patternIds` から該当IDを除外。
  - `patternIds` が空になった勤務者は一覧から除外。
  - 保存・再描画・メッセージ表示。

### 1.3 勤務者管理
- `addWorker` クリック時:
  - 入力検証（氏名、勤務体系選択、月間公休日数、希望休）。
  - `workers` へ `{ name, patternIds, requiredDaysOff, requestedDaysOff }` を追加し再描画。
- 削除ボタン押下時:
  - 対象勤務者を `workers` から除外して再描画。
- 名前変更ボタン押下時:
  - 現在の名前を初期値として新しい名前の入力を受け付ける。
  - 空文字と重複名を拒否し、勤務可能体系・公休日数を維持したまま名前を更新する。
- 希望休編集ボタン押下時:
  - 登録済み希望休を日付チェック欄へ反映し、更新またはキャンセルを受け付ける。
  - 月間公休日数を超える希望休は拒否する。

### 1.4 テストパターン読み込み
- `test-pattern.js` に定義した勤務体系、勤務者、時間帯別必要人数、公休日数を画面状態へ反映する。
- 読み込み時に既存の勤務体系・勤務者をテストパターンで置き換える。

### 1.5 シフト作成実行
- `generate` クリック時:
  - 入力値を収集し、Web Workerへ最適化処理を依頼する。
  - 計算中は進行状況とキャンセルボタンを表示する。
  - `renderScheduleAlternatives()` と `renderSchedule()` で結果・必要ヘルプ・代替案を表示する。

### 1.6 勤務人数対象外時間管理
- 担当者候補、対象日、時・分の選択欄から組み立てた15分単位の開始・終了時刻を `absenceRules` へ追加する。
- 編集時は同じIDの条件を更新し、削除時は配列から除外する。
- 勤務者名変更時は候補名を追従し、勤務者削除時は候補から除外する。候補が空になった条件は削除する。

### 1.7 シフト出力
- CSV出力:
  - `exporter.js` で担当者別の表をCSV文字列へ変換する。
  - UTF-8 BOM付きBlobを生成し、`autoshift-YYYY-MM.csv` としてダウンロードする。
- Googleスプレッドシート出力:
  - 担当者別の表をTSV文字列へ変換してクリップボードへコピーする。
  - `https://sheets.new` を開き、A1セルへの貼り付けを案内する。
- 画面、CSV、Googleスプレッドシートへ同一の表を出力し、各勤務者行の末尾列へ勤務日数を出力する。
- 画面には、日付・時間帯ごとに勤務者名を集計した表も追加表示する。この表はCSV・Googleスプレッドシートには含めない。

## 2. 出力変換詳細設計（exporter.js）
### 2.1 `buildScheduleTable(result, workerNames)`
- 勤務者を行、日付を列とする二次元配列を生成する。
- 割当がないセルには `公休` を設定する。
- 各勤務者行の最終列に勤務日数を設定する。
- `①`・`夜`の翌日に`明`、その翌日に`公`、`③`の翌日に`明`を設定する。`明`は勤務日数と連続勤務日数へ加算する。

### 2.2 `calculateWorkDays(result, workerNames)`
- 日別割当を集計し、勤務者ごとの勤務日数を返す。

### 2.3 `toCsv(rows)` / `toTsv(rows)`
- 区切り文字、引用符、改行を含むセルを二重引用符で囲む。
- セル内の二重引用符は二重化する。

## 3. シフト作成詳細設計（scheduler.js / milp-scheduler.js）
### 3.1 補助関数
- `buildHourRange(startHour, endHour)`:
  - 勤務時間帯を時刻配列へ展開（跨日対応）。
- `buildQuarterRange(pattern)`:
  - 開始・終了時刻を15分単位の勤務枠へ展開し、`breaks` の休憩枠を除外する。
- `daysInMonth(year, monthIndex)`:
  - 対象月の日数取得。
- `normalizeWorkerPatternIds(worker)`:
  - 勤務者が選択した勤務体系IDを取得する。

### 3.2 事前検証
- 対象月形式、勤務者配列、勤務体系配列、月間公休日数、必要人数配列を検証。
- 勤務体系ごとに15分単位の勤務枠配列を前計算し `patternMap` を生成。
- 勤務者ごとに勤務可能勤務体系を解決し、内部データへ変換。

### 3.3 割当アルゴリズム
- `milp-scheduler.js` が担当者・日付・勤務体系ごとの0/1変数を持つ混合整数計画モデルを生成する。
- 月間公休日数、希望休、時間帯別必要人数、明・公、4連勤、夜勤回数、勤務遷移、勤務体系回数を線形制約として同時に解く。
- 時間帯別の外部ヘルプ人数を0以上の整数変数とし、最優先で15分単位の合計ヘルプ量を最小化する。ヘルプ量へ影響しない小さな評価値で総勤務時間を評価し、余剰配置が少ない勤務体系を優先する。
- `solver-worker.js` がHiGHS WebAssemblyを読み込み、最適化をメインスレッド外で実行する。
- 同一の勤務条件・希望休・勤務人数対象外条件を持つ担当者グループを循環置換し、同じ最小ヘルプ量を維持した代替案を最大3件生成する。

### 3.4 業務ルールの制約化

| 要件ID | 制約化方法 |
| --- | --- |
| BR-01 | 担当者・日付ごとの勤務割当変数、`明`を発生させる前日変数、`公`を発生させる前日または前々日変数の合計を1以下とする。 |
| BR-02 | 対象月の日数から月間公休日数を引いた値と、勤務割当および`明`の合計を一致させる。 |
| BR-03 | 希望休の日は勤務割当変数と`明`を発生させる変数の合計を0とする。 |
| BR-04 | 連続する5日間について、勤務割当および`明`の合計を4以下とする。これにより4連勤を許可し、5連勤を禁止する。 |
| BR-05〜BR-08 | 勤務体系名と`nextDayOff`から翌日・翌々日の占有条件を生成し、該当日は他の勤務割当を禁止する。 |
| BR-09 | 夜勤開始日の間隔を、`③`は2日、`①`・`夜`は3日として夜勤周期を列挙し、連続する3周期の夜勤割当合計を2以下とする。 |
| BR-10 | 担当者ごとに全日程の`M`・`R`・`L`割当変数を加算し、`①`割当変数の合計を引いた値を0とする。 |
| BR-11・BR-12 | 隣り合う2日について、禁止される勤務体系の組合せに対応する割当変数の合計を1以下とする。 |
| BR-13 | 日付・15分枠ごとに勤務中の割当変数を加算し、勤務人数対象外変数を減算した人数を必要人数以上とする。休憩枠は勤務中の変数へ含めない。 |
| BR-14 | ヘルプ1枠の評価差より必ず小さくなる係数で各勤務体系の勤務枠数を目的関数へ加え、ヘルプ最小化を妨げずに総勤務時間を副次評価する。 |
| BR-15 | 対象条件ごとに候補者選択変数を設け、該当時間をすべて勤務する候補者からちょうど1人を選ぶ。 |
| BR-16 | 日付・15分枠ごとに0以上の整数のヘルプ変数を加え、全ヘルプ変数の合計を目的関数として最小化する。 |
| BR-17 | 勤務条件が同一の担当者グループ内で担当者名を循環置換し、制約とヘルプ量を変えない代替案を構成する。 |

### 3.5 最適化結果の判定
- HiGHSが最適解を返した場合、勤務割当変数と勤務人数対象外変数を結果へ変換する。
- 外部ヘルプ変数が0の場合は登録勤務者だけで成立するシフトとして扱う。
- 外部ヘルプ変数が正の場合は、同じ日・同じ人数で連続する15分枠を開始・終了時刻へまとめる。
- 制限時間内に実行可能解が見つからない場合は、利用者向けのエラーを返す。

### 3.6 出力整形
- 成功時:
  - 日付・勤務者・勤務体系名を `assignments` として返却。
  - 連続する同人数のヘルプ枠を結合し、`helpRequests` として返却。
  - 代替案を `alternatives` として返却。
- 失敗時:
  - `success: false` とエラーメッセージを返却。

## 4. 既知の仕様制約
- 勤務者情報はブラウザ再読込で消える（永続化しない）。
- サーバー処理やDB連携は実装しない。
